# Neon Void Rework — 전투 플러그인 남은 4종 및 차단 조건

> **총괄 A / 통합 검증 전용.** [Draft PR #120](https://github.com/tharu8813/Neon-Void/pull/120).
> GDD의 [확정], [초안 v0.1], [미확정] 구분을 유지한다.
> 이 문서는 실제 배포 승인이나 보호막 최종 규칙 확정을 의미하지 않는다.

## 코드 경로 차이 주의

- **C #117**의 `plugin_b_live_runtime.gd` 독립 전투 상태 검증은 27개 중 23개가 합격했다. 다음 4개는 여전히 독립 경로의 미검증 항목: `nv_c_periodic_shield`, `nv_c_skill_shield`, `nv_r_dash_shield`, `nv_c_random_rare`.
- 실제 A 선택형 CPU 파일럿은 **B #119** `production_cpu_adapter.gd` → `c_effect_adapter.gd` → C `plugin_effect_runtime.gd`을 사용한다. 독립 C 경로와 생산형 B 경로는 같지 않으므로 23/27 테스트만으로 장면에서의 27종 실행을 증명할 수 없다.
- A의 `tests/rework/integration/provisional_shield_contract_cases.gd`는 **생산형 B의 실제 damage calculation과 HP ledger**를 사용한다. C가 tick / `skill_cast` / dash 이벤트에서 3개 보호막 제안을 발생시키고, B가 실제 true damage보다 먼저 적용해 체력을 보호하고 보호막 소진 후 추가 피해를 정상 전달하는지 확인한다. 이는 현재 코드의 **제안된 shield-first** 동작이 연결되어 있음을 뜻하며, 정식 승인된 방어 규칙/밸런스나 실기기 연출 완성을 뜻하지 않는다.
- 보호막 3종 중첩·유효시간·오버힐·피해 종류별 경감 순서·CC·흡혈·피해량 0에서의 on-hit와 proc 규칙은 아직 승인되지 않았다. 임의로 공식 확정하지 않는다.

## P0 소유자별 남은 구현

| 작업 | 소유자 | 완성 기준 |
| --- | --- | --- |
| 주기·스킬·대시 보호막 세 종류 | B + C | 한 가지 승인된 전투 경로를 사용; shield-first 또는 후처리의 **정책 승인** 후 체력/방패/흡혈/DoT/사망 순서를 확정·통일; 모든 등급/레벨/B 실전 단위 테스트 |
| `nv_c_random_rare` 신규 레어 획득 | C + E + A | C는 플러그인 획득을 **E 성공 ACK 이후에만** 이벤트화; 레어 풀·후보와 재현 가능한 난수 상태, 고유 영수증·재시도/중복 방지; E는 원자적으로 승인/지급; A는 UI·C/B 업데이트를 ACK 뒤에만 진행 |
| 현재 C #117의 23/27 결과 통합 | B + C | 테스트한 독립 subclass와 실제 CPU 생산형 adapter의 코드·트리거 일치 확인; 동일 결과를 실제 B/D CPU scene에서 검증 |
| 보호막 및 레어 지급 실패 시 안전성 | E + A | 저장 거부/정전/재실행/중복 이벤트에서 레벨·랜덤 레어 중복 지급 금지; 모호하면 일시 정지·읽기 전용 재동기화 |

## 무작위 레어 보상 경계

- GDD에는 **무작위 레어 플러그인 획득** 효과가 기재돼 있지만, 구체 후보 우선순위, 이미 최대 레벨인 레어 처리, 2레벨 추가 수량, 보상 UI, 난수 시퀀스 및 재시작 중간 상태는 전부 확정된 것이 아니다.
- 현재 C `grant_rare`는 `rare_reward_request`를 출력하되 B `c_effect_adapter._validate_commands`는 실제 지급을 **거절**한다. 이유는 E의 보상 영수증이 필요하기 때문이다. 이것이 안전한 현재 동작이다.
- **금지:** UI에서 임의 레어를 먼저 선택, C에만 메모리 레벨 지급, 일반 `plugin_picked` 영수증을 허위 생성, E에 없는 카드 선택을 강제 저장, Level 2에서 임의의 추가 지급 수 확정.
- 개발 제안: E가 제공하는 단발성 이벤트 보상 트랜잭션과 C의 동일 난수 카드 스냅샷을 하나의 원자적 기록으로 남기고, 트랜잭션 성공 전까지 보상 알림도 확정하지 않는다.

## 이미 해결된 다른 P0 경계

- A 파일럿에서 **CPU 맵 생성보다 먼저** E가 해당 `map_seed` 및 `D-procedural-v1` 생성기 버전을 `checkpoint_region` 트랜잭션으로 저장·ACK한다. D는 ACK 없이 CPU 맵을 만들지 않는다.
- C 3장 카드, 단일 재추첨, RNG 상태를 E에 먼저 저장한 후 UI 공개; 획득은 `prepare → E commit → C confirm → B effect`.
- 통합 자동 테스트는 Windows/Linux headless이며 CPU 일반 조작감, GPU 렌더 타이밍, 오디오, 화면 해상도 및 장시간 8~12분 밸런스 테스트는 포함하지 않는다.
