## 2. 신화급 신규 제안 [전부 초안, 선택/승인 필요]

| 아이디어 | 빌드 규칙 변화 | 필요한 보호장치/시각 피드백 |
|---|---|---|
| **분기 컴파일러** | 서로 다른 적중 효과가 연속 발동하면 다음 공격이 마지막 효과 둘을 순서대로 재실행 | 효과 재진입 경로 추적, 원형 참조 금지, 과도한 VFX 합치기 |
| **재부팅 프로토콜** | 의뢰 내 특정 조건에서 한 차례 치명상 회피 대신 일시 패널티 부여 | **복제 횟수/최종 파기 회복 금지**. 백신 복제와 혼동 금지 |
| **병렬 처리** | 일정 시간 동안 공격 기원을 둘로 분기하되 합법적인 적중 연쇄 유지 | 동일 영수증/XP 중복, 원본과 복제 발사체 소유 태그 필요 |
| **오버클럭 특이점** | 피해/공격속도 상승과 위험 환경 가중치가 함께 적용되어 위험을 감수하게 만듦 | 무적/0쿨타임·무한피해 루프 금지. 밸런스 QA 필수 |

**추천 도입 방법:** 우선 신화가 없는 27종만으로 전투 조합 기반을 완성 → 데이터/연쇄 병목 테스트 → **적어도 2종 이상의 신화 후보를 실제 보스/구역에서 시험** → 사용자 승인 후 정식 편입. 신화를 임의로 배포할 필요는 없다.

## 3. 카드 추첨/리롤 계약 [확정]

1. 한 보상 화면에 **3장**, 슬롯마다 등급을 개별 추첨.
2. 확률 입력: 현재 정화 개수, 선택한 구역 난이도, 행운. **[확정] D-006 (2026-11-22): 후보 B. 곡선** — 기본 가중치 일반 80 / 레어 18 / 전설 2 / 신화 0, 행운 1p당 전설 +3.5%, Hard 전설 x1.45 · Easy x0.85, 정화 1곳당 전설 +35%. 수치는 `Runtime/Plugins/RewardRollTable.cs`, 근거는 `docs/D006_REWARD_SIMULATION.md`.
3. 유저가 선택한 **한 슬롯만** 다시 추첨하고, 새 등급 + 새 플러그인 종류를 구한다. 나머지 2장 유지.
4. 의뢰당 기본 **리롤 3회**, 이벤트 추가 가능.
5. 전설 또는 신화가 화면에 5회 연속 나타나지 않았다면 **그 다음 보상 화면부터 확률 보정이 점진적으로 적용**된다. '미등장 5회'는 15장 각 카드를 따로 세는 것이 아님. **[확정] D-006: 화면당 +0.7, 상한 x6, 리셋은 리롤로 뽑은 것을 포함해 화면 어디든 전설+가 보이면.**
6. 같은 플러그인 획득 = 레벨 상승, 현재 최대로 강화된 플러그인은 후보에서 제거. 개별 maxLevel·다음 단계 효과는 데이터로 정의.
7. 보상 선택, 리롤 결과, 희귀 보너스 원본/파생 효과, 천장 카운트, RNG 위치는 영수증과 함께 하나의 논리 상태로 관리.

**[확정] D-006·D-007 (2026-11-22):** 천장 리셋 시점(리롤 포함 화면 단위), 초기 확률표와 상승폭, 후보 고갈 처리(낮은 등급의 미보유 후보로 대체, 전체 부족 시 유효한 것만), 같은 화면의 동일 후보(금지). 수치는 데이터(`RewardRollTable`)로 분리되어 있어 D-011 재튜닝이 한 파일 수정이다.

**[미확정]** 순서별 롤, 보상 화면 닫기 정책, 의뢰당 보상 화면 수. 플레이어의 영구 보상 정책을 자동 확정하지 않는다.

**[초안]** 화면 난수는 `seed+runId+rewardScreenId+slotId+rerollIndex`를 기록한 **별도 RNG stream**에서 재현한다. 슬롯1 재추첨이 슬롯2·3 결과나 전투 RNG를 바꾸지 않아야 한다. '리롤 눌렀는데 등급은 고정'은 버그.

## 4. 플러그인 효과 데이터 설계 [개발 권장]

권장 필드:

```text
PluginDefinition
  StableId, DisplayNameKey, DescriptionKey, Rarity
  Learnable, MaxLevel, LevelEffectDefinitions[]
  TriggerTags[], AllowedProcSources[], ProcInternalCooldownScope
  DamageDefinition {type, base, adRatio, apRatio, area, periodic, canCrit}
  StackingPolicy, StatModifiers[], ProjectileModifiers[]
  VisualCueId, SoundCueId, SchemaVersion
PluginInstance
  InstanceId, DefinitionId, Level, AcquiredRunId, OriginReceiptId, IsLearned, OwnerLocation
```

`StableId`는 사용자 저장에 처음 사용한 후 무단 변경 금지. `InstanceId`는 같은 정의를 DB에 여러 번 들 수 있는지 확정될 때까지 지원 가능한 형식만 설계하고 실제 허용 정책은 보류. `OwnerLocation = RunCarried | Archive | PendingExtraction` 등은 DB 중복 복제 금지를 위해 필수.

## 5. 여러 탄환 형태의 합성 [미확정, 임시 실험 제안]

**핵심 갈등:** 출전 플러그인 수 무제한, 레이저/부메랑/유도탄/추가탄 등은 모두 독립적임. 그중 어느 것 하나를 강제로 끄는 것은 기획 의도에 맞지 않는다. 하지만 레이저이면서 부메랑인 공격의 타격 방식은 원안에 확정된 것이 없다.

**[초안 우선 실험 모델]**

```text
AttackOrigin
  → FireTiming (부메랑이 돌아오면 다음 기본공격 가능)
  → ShotMultiplicity (추가 발사체/4중 연사)
  → TrajectoryTraits (유도/왕복/직선, 정규화 우선순위 전략)
  → HitShapeTraits (빔/물리 탄환/영역/관통)
  → Damage + ProcEfficiency per hit
  → Presentation-only geometry
```

- 각 형태는 **효과 계층**에 등록하고 단독/두 개/세 개 동시 조합에 대한 기대 결과를 표로 먼저 작성.
- [초안 예시] 레이저+부메랑이 동시라면 왕복하는 빔 발사체 또는 주기성 레이저 방출형 부메랑을 A/B 테스트. 승인이 없어도 **임시 Prototype 조합**으로 테스트할 수 있지만 영구 확정 효과로 기록 금지.
- 각 발사체가 적중할 때 원본·파생 태그와 적중 효율(70%/80% 등)을 유지. 발사체가 2개가 되더라도 XP/영구 보상은 피해 원인과 독립.
