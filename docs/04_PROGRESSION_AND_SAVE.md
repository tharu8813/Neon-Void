# Progression · Clone · Database · Save Contract | v2.0

> **데이터 무결성은 보상 연출보다 우선한다.** 과거 Godot/Python 이식에서 중요했던 '보상 선지급/중복 지급/강제 종료 후 중단 처리' 문제를 처음부터 막는 신규 Unity 설계. 실제 Unity 저장 구현을 완료했다고 주장하는 문서가 아니다.

## 1. 세 가지 상호 다른 상태

| 영역 | 수명 | 주요 데이터 | 권한/영속성 |
|---|---|---|---|
| **전역 설정** | 백신과 독립 | 그래픽·음량·언어·키 바인딩·접근성 | 백신 최종 파기에서도 보존 [확정] |
| **백신 영구 상태** | 백신 생성→최종 파기 | 백신 Lv/XP·포인트·영구투자·습득 스킬·보관 DB·출전 학습 플러그인·복제 잔여·기록 | 복제 사망으로 확정 상태 유지, 최종 파기 시 해당 백신만 초기화 [확정] |
| **의뢰 상태** | 한 의뢰 시작→성공/사망/중단 | runId·시드·정화·임시 Lv/XP·임시 플러그인·리롤·천장·환경·맵 생성 버전·미정산 보상 | 새 의뢰 Lv.1, 사망 후 임무 재생성 [확정] |

**규칙 핵심:** 백신 레벨과 의뢰 레벨을 한 변수로 혼합하지 않는다. `VaccineXP`는 영구 점수, `RunXP`는 임시 카드 지급. [초안] 백신 레벨 1당 영구 포인트1, 임무 레벨 100+30(L-1) XP, 백신 레벨 180+90(L-1) XP, 기본 720 임무 XP/구역. **조정 전 승인 불필요한 밸런스 초안이지만 사용자 확정 수치가 아님**. 모든 값은 데이터로 분리.

## 2. 복제 및 파기 [확정]

| 누적 사망 | 사망 전 잔여 복제 | 사망 후 상태 | 대상 자산 |
|---:|---:|---|---|
| 1번째 | 3 | 잔여 2, 허브에서 재시도 | 출전 플러그인 소실/DB보관·기존 XP 유지 |
| 2번째 | 2 | 잔여 1, 허브에서 재시도 | 동일 |
| 3번째 | 1 | 잔여 0, 허브에서 재시도 | 동일, **다음 사망이 마지막** |
| **4번째** | 0 | **최종 파기**, 백신 선택 화면 | 해당 백신 영구/의뢰 성장·스킬·DB·소지·관련 기록 파기 |

- 복제 회복은 어떤 수단으로도 불가. '복제 0'은 **죽은 상태가 아니라 마지막 기회**.
- 사망한 의뢰는 실패하고 **다음 의뢰는 새 시드·새 적**. 진행 중 전투를 그대로 이어하지 않는다.
- 사망한 의뢰의 **미정산 영구 XP·성장 포인트 중 20~70%** 정산, 기준은 진행도. **이미 승인된 영구 XP/포인트**는 빼앗지 않는다.
- **[초안] 보존율** `min(70%, 20% + 10% × 정화 구역 수)` = 0개20%, 1개30%, ... 5개70%. 무조건 확정 계산식으로 취급하지 않는다.
- **사망하지 않은 앱 중단/강제 종료/크래시**는 절대 복제 차감/파기 트리거가 아니다.
- 최종 파기 과정에서도 **화면/음량/키 설정 및 다른 백신 슬롯**은 보호.

## 3. 플러그인 데이터베이스 [확정]

1. 일반·레어 플러그인은 **성공 철수 후 0~2개 새로 학습** 가능. 학습할 때 레벨을 유지한다.
2. 전설·신화는 **학습 불가**. 의뢰 중 일시적으로만 사용.
3. 학습된 플러그인의 **보관 DB 용량 무제한**, 출전/현재 소지 플러그인의 개수 제한 없음.
4. 보관 DB에서 출전 목록으로 꺼내면 **DB에서 사라진다**. 둘 사이에서 '복사'하는 것이 아니라 동일 소유 인스턴스의 이동이다.
5. **사망 시 출전 소지분은 소실**. 성공 철수에서 살아 돌아온 학습 소지분은 **자동 DB 입고가 아니다**. 플레이어가 직접 DB로 넣어야 한다.
6. 4번째 사망에서 해당 백신에 속한 DB까지 파기.

**[미확정, 특히 중요]** 성공 철수에서 기존 출전 학습 플러그인의 보관 가능 여부/신규 학습 2개 한도와의 관계, 동일 정의 인스턴스 복수 허용 여부, 서로 다른 백신 사이 공유 여부. 즉각 손실이 발생할 수 있는 규칙이므로 **보상/DB 영구 변경 전 사용자 승인**을 받아야 한다. 현재는 소유권을 잃지 않는 데이터 모델과 UI의 경고/가드만 먼저 구축.

## 4. 저장 데이터 분리: 레거시 절대 보존

**레거시 Python 파일 (기존 프로젝트 루트 또는 Windows `%LOCALAPPDATA%\NeonVoid`):**

```text
save.json
settings.json
profile.json
antivirus_db.json
os_checkpoint.json
```

- 위 5개 및 Godot의 과거 저장 파일을 Unity가 자동 탐색·파싱·변환·초기화/덮어쓰기하지 않는다. 기존 Python 프로젝트는 `python/` 아래 **읽기 전용 참조**.
- **[신규 제안] Unity 세이브**는 `Application.persistentDataPath` 아래 제품 구분 하위 디렉터리 `NeonVoidUnity/v1/`에 `global_settings.json` 및 개별 백신 슬롯 문서, 별도의 백업/저널/영수증 파일로 격리. `persistentDataPath`의 실제 물리적 위치는 런타임에서 확인하고 이전 경로와 충돌하지 않도록 단위 테스트.
- 테스트용 저장 서비스는 반드시 임시 디렉터리를 주입받으며 실제 사용자 저장 디렉터리에 접근하면 테스트 실패.
- **미래에 명시적 가져오기 기능이 생긴다 해도**, 사용자 선택한 원본만 **읽기 전용으로**, 변환은 별도의 신규 슬롯 생성, 파일 해시/백업/검증/결과 확인 후 종료. 지금 개발 범위에는 **자동 이식 없음**.

## 5. 원자적 저장/영수증 [개발 필수]

### 권장 명령과 영수증 타입

| 도메인 명령 | 필수 사전조건 | 성공 이후에만 반영 | 재시도 정책 |
|---|---|---|---|
| `BeginRun(runId,seed)` | 백신 살아있음/다른 의뢰 없음 | 메인보드 진입 | 같은 runId 중복 시작 금지 |
| `EnterHardware(area,seed,genVer)` | 선택 가능한 곳/런 활성 | 해당 맵 생성 | 동일 seed/genVer 재사용 |
| `PresentReward(rewardId,3cards,rng)` | 중복 미제시 | 카드 확정 표시 | 동일 카드/난수 재표시 |
| `RerollCard(rewardId,slot,rollIndex)` | 리롤 충분/보상 미정산 | 새 카드·리롤 잔여 갱신 | 동일 rerollId 다시 소모하지 않음 |
| `ClaimReward(receiptId,pluginId)` | 제시 카드 중 하나·미정산 | 임시 인벤토리/전투 적용 | ACK 재요청 때 기존 결과 조회 |
| `ClaimRandomRare(parentReceipt,rareReceipt)` | G15 트리거+유효 후보 | 원본/파생 **동시** 승인 | 일부만 적용 금지 |
| `CleanseHardware(area,receiptId)` | 목표/보스 완료 | 정화 상태·철수 활성/XP | 중복 보상 없음 |
| `ExtractRun(receiptId,learnIds)` | 최소 1개 정화·학습 일반/레어 0~2 | 영구 XP/포인트/신규 학습/귀환 | 이중 철수/보상 차단 |
| `RegisterDeath(deathId)` | 실제 전투 사망, 런 활성 | 1~3회 복제 차감·보존 보상·출전 소실 또는 4회 파기 | 중복 deathId로 두 번 차감 금지 |
| `MovePlugin(instanceId,src,dst)` | 동일 소유 인스턴스, 허브 상호작용 | DB↔출전 이동 | 원본과 목적지 중복 소유 금지 |

### 권장 저장 트랜잭션 단계

```text
1. command 유효성/슬롯세대/버전/nonce/수량/소유권 검사
2. 현재 영속 상태 + 입력에서 불변 snapshot(next) 계산
3. next와 영수증을 같은 트랜잭션 단위로 직렬화
4. 임시 파일 완전 쓰기 → flush/fsync 가능 범위 → 체크섬 검증
5. 이전 정상본 백업 → atomic replace/rename(가능한 플랫폼 범위 확인)
6. 저장 결과를 재읽기/검증 → 성공 ACK
7. **그 다음에만** UI·전투·성장 서비스에 반영 이벤트 발행
```

- 파일시스템에 진정한 다중 파일 원자성이 보장되지 않으면 **한 개의 snapshot+receipt log/journal** 또는 트랜잭션 영속 저장을 사용. '2개의 JSON을 각각 저장'한 뒤 원자적이라고 주장하지 않는다.
- `runId`, `vaccineId`, `vaccineGeneration`, `receiptId`, `commandNonce`, `schemaVersion` 등 중복 방지용 불변 키. 완료된 command를 다시 보낼 때는 **같은 결과를 반환**.
- `write succeeded / response lost`: 영수증으로 실제 확정 여부 확인. 랜덤 보상 다시 뽑기 금지.
- `write failed / torn`: 마지막 검증된 정상 스냅샷을 복구. 데이터 불일치 시 사용자 데이터를 덮어쓰지 않고 **읽기 전용 복구/오류 상태로 정지**.
- 체크포인트/중단 의뢰 재개 정책이 미확정인 동안은 **의뢰 재개·취소·보상 확정을 자동 실행하지 않는다**. 마지막 승인 상태를 안전하게 남기고 경고/상태 페이지 제공.

## 6. Unity 신규 스키마 [초안 JSON 윤곽]

```json
{
  "schemaVersion": 1,
  "product": "NeonVoidUnity",
  "saveSlotId": "slot-1",
  "vaccine": {
    "id": "vaccine-uuid",
    "generation": 1,
    "alive": true,
    "copiesRemaining": 3,
    "permanentLevel": 1,
    "permanentXp": 0,
    "unusedStatPoints": 0,
    "permanentInvestments": [],
    "learnedSkills": [],
    "equippedSkills": [],
    "archivePluginInstances": [],
    "carriedPluginInstances": []
  },
  "run": null,
  "processedReceiptIds": [],
  "snapshotRevision": 1,
  "snapshotChecksum": "computed-on-save"
}
```

의뢰가 활성이라면 `run={id,seed,generatorVersion,missionLevel,missionXp,cleanedHardwareIds,mapSeedByHardware,environmentByHardware,plugins,rngStreams,rerollsLeft,pityCounter,pendingRewards,uncommittedXp,uncommittedPoints,status}`. 이 예시는 **API 설계 윤곽**이지 구현됐다는 뜻이 아니다. 수많은 `processedReceiptIds`를 계속 본문 배열에만 저장하면 파일 크기가 증가하므로 압축/시대 구분/데이터베이스 전략 [초안].

## 7. 명세상 위험한 경계와 QA

| 상황 | 허용 결과 | 금지 결과 |
|---|---|---|
| 3번째 사망 | 복제 잔여 0, 허브 복귀 | 즉시 최종 파기 |
| 4번째 사망 | 해당 백신 성장/DB 파기, 새 백신 선택 | 전역 옵션·타 백신·레거시 기록 파기 |
| 정화 0개 철수 | 성공 불가 | 보상 지급 |
| 정화 1개 철수 | 성공 가능 | 5개 완주 강요 |
| 저장 실패 | 보상 미확정·상태 유지 | UI 먼저 '보상 획득 완료' |
| 저장 성공 ACK 유실 | 기존 영수증 조회 | 레어 카드/포인트 재발급 |
| 사망 직후 앱 강제 종료 | 마지막 확정 사망영수증으로 1회 복구 | 복제 2회 차감 |
| 강제 종료만 발생 | 자동 복제 차감/파기 없음 | 강제종료를 사망 처리 |
| DB 출전 이동 | DB에는 인스턴스 없어짐 | DB+소지 중복 잔존 |
| 전설/신화 획득 후 철수 | 임무 전용, 학습 후보 제외 | 영구 DB 보관 |
| 진짜 오래된 세이브/미래 스키마 발견 | 레거시 변경 금지/안전 오류 | 자동 변환·삭제 |

**테스트 시나리오:** synthetic fixture로 파일 쓰기 권한 없음, 임시 파일 손상, 이름 충돌, 다중 저장/재시도, 중단된 checksum, 동일 사망/철수/보상 100회 중복 호출, 프로세스 kill 직전/직후 재실행, 복제 3→2→1→0→파기. **정식 사용자 세이브를 QA fixture로 활용하지 않는다**.
