# Neon Void Rework — A 통합 파일럿 개발·QA 현황

> **상태:** 신규 GDD 기반 CPU 1개 구역의 **별도 실행 파일럿**. 기존 기본 게임을 대체하지 않으며 **릴리스 준비 완료가 아님**.  
> **통합 검증 PR:** [#120](https://github.com/tharu8813/Neon-Void/pull/120) (Draft, **병합 금지**) · 기반 [#115](https://github.com/tharu8813/Neon-Void/pull/115)  
> **원기획:** [NEON_VOID_GDD_V1.md](NEON_VOID_GDD_V1.md) · [누락 기능 #108](https://github.com/tharu8813/Neon-Void/issues/108)  
> **검증:** Godot 4.7.2 Windows/Linux headless CI. 사람이 플레이한 Windows QA를 뜻하지 않음.

## 실행 경로 구분

| 진입 경로 | 동작 |
| --- | --- |
| 프로젝트 기본 실행 (`scenes/main.tscn`) | **기존 4 OS 구역 Godot 게임**, 변경 없음 |
| `scenes/rework/world/cpu_vertical_slice.tscn` F6 | D 소유 CPU 독립 데모; `demo_mode=true`로 보상 **저장하지 않음** |
| **`scenes/rework/integration/rework_pilot.tscn` F6** | A 소유 **저장형** CPU 파일럿; B 정식 60Hz 전투, C 효과·카드, E 승인·저장·A 이벤트 연결. 기존 main 유지 |

**주의:** A 저장형 파일럿은 실행하면 새 별도 테스트 슬롯을 만든다. 저장 데이터가 실제로 생성되므로 실기기 QA 승인 전에는 중요한 플레이 기록에 사용하지 말 것.

## 현재 통합된 것

- D의 실재하는 3D 디펜더 허브/메인보드/CPU 한 구역을 별도 씬으로 실행할 수 있음.
- 허브에서 의뢰 시작 요청 → E 신규 스키마에 **`start_mission` 먼저 저장** → D 메인보드 입장.
- 실제 CPU 하드웨어 게이트 → D가 고유 맵 시드와 `Maps.GENERATOR_ID = "D-procedural-v1"`를 제시 → A가 E `checkpoint_region`을 **원자적으로 저장** → 승인 후에만 D가 CPU 맵과 플레이 장면을 생성. 실패/모호한 ACK는 전체 시뮬레이션 안전 정지. 기존 데모 장면은 영구 저장하지 않음.
- B #119 정식 60Hz 전투와 D #116 월드 라우터의 실제 적 사망 신호 → E 의뢰 경험치 저장 → C의 3장 카드 UI. 별도의 A 통합 테스트는 재현성을 위해 합성 적 처치 이벤트도 사용함.
- C 카드 생성/재추첨 → E #118에서 **정확한 3장과 RNG 커서·재추첨 카운트 먼저 체크포인트** → UI 노출. 선택 시 `prepare_card` → E `plugin_picked` 영구 기록 → C `confirm_card` → B/C 실전 능력치 레벨 반영. 저장 실패/응답 불확실 시 게임 전체 일시 정지. 메모리에서 카드 선택만으로 인벤토리 선지급하지 않음.
- 보상 선택 중 `SceneTree.paused`를 켜되 D 월드는 PAUSABLE, A UI만 ALWAYS. 나머지 전투 처리를 멈추고 카드 선택 후 해제.
- D `objective_completed` / `hardware_cleansed` 사실은 A가 E 영수증을 기록한 뒤 D에 ACK. 보스 사실은 정화 보상을 이중 지급하지 않음.
- CPU 정화 후 철수 시 **0~2개 신규 일반·레어 플러그인을 플레이어가 직접 선택**하고, `extract` 트랜잭션이 승인되었을 때만 허브 귀환. 기존 학습 플러그인은 E 미확정 재학습 정책에 따라 후보에서 제외.
- 귀환한 **소지 플러그인을 허브에서 수동으로 보관** 가능; `archive_plugin` 트랜잭션 사용.
- 사망 사실도 E의 `die`에 안전하게 저장한 뒤 D에게 ACK. 1·2·3회 사망은 복제 소모, 4회 파기는 데이터 삭제·백신 선택 상태; 파일럿에 명시적인 새 백신 선택 UI 버튼 제공.
- 슬롯·실행 오류 시 게임 상태를 동기화 없이 전진시키지 않고 플레이를 멈춤. 기존 Python/root JSON 및 구 Godot 세이브를 건드리지 않음.
- **스킬 발견 초안:** `hardware_cleansed`를 E가 승인한 **뒤에만** 3장 초안을 연다. 후보는 의뢰 시드·정화 구역·이미 습득한 스킬로 결정되며 별도 저장 테이블을 만들지 않는다. 선택 시 E `learn_skill` 한 트랜잭션(습득+3슬롯 장착)으로 저장하고, **새 리비전 readback 뒤에만** B의 스킬 로드아웃을 교체한다. 중단/모호한 ACK는 재시도하지 않고 안전 정지한다. 스킬 9종은 GDD 11이 `[미확정]`이라 플레이 가능한 **BALANCE_DRAFT**다.
- **보스 압박 초안:** 5개 보스 역할에 방사/직선/유도/레일/지진 패턴을 부여했다. 첫 패턴은 150틱 유예, 발사 42틱 전에 링 텔레그래프를 표시한다. 수치는 BALANCE_DRAFT이며 일반 역할 없는 fixture 적은 기존 동작을 유지한다.
- **필드 회복 초안:** 목표 정화 E ACK 직후 D가 최대 HP/마나의 15%를 회복한다. 승인된 GDD 수치가 아닌 BALANCE_DRAFT이며 보상 원장·저장 파일을 건드리지 않는다.
- **연출:** B 투사체가 팀/스킬별 발광·속도 스트레치로 표시되고, 점멸은 D 타일 벽을 통과하지 못한다. 파일럿은 기존 절차적 신스(`scripts/audio/legacy_synth.gd`)를 재사용한 사운드와 글로우/안개 환경을 사용한다.

## 저장 경계

- 기본 테스트 슬롯: `user://rework/v1/rework-slot-integration-pilot/`; Godot의 프로젝트별 user 디렉터리 내부.
- CI는 각 실행마다 **유일한 합성 슬롯** `pilot-smoke-<PID>-<ticks>`를 생성하고 테스트 후 해당 합성 경로만 제거.
- 초기화는 슬롯 디렉터리가 **완전히 없는 경우에만** 허용; 기존 슬롯이 손상되거나 저장 도중 중단된 상태라면 **자동 덮어쓰기·자동 복구·새 게임 시작을 하지 않음**.
- 미완성 의뢰가 저장된 상태에서 앱이 종료되면 **재개/의뢰 취소 규칙이 아직 승인되지 않았으므로 진입 차단**. 스토어의 명시적 오프라인 복구 계약을 따름.
- 미래 저장 스키마, 오프라인 잠금, 중복 영수증, 저장 실패 시 사용자 데이터를 억지로 되돌리지 않음.
- 현재 파일럿을 반복 실행하면 **동일한 통합 파일럿 슬롯**을 이어서 사용하므로 QA 결과 저장을 실제 개인 플레이와 혼동하지 말 것.

## 자동화된 검증

`tests/rework/integration/rework_pilot_smoke.gd`는 다음을 Linux 및 Windows에서 확인한다.

1. 별도 신규 슬롯의 안전한 생성.
2. D 허브에서 E 신규 의뢰가 먼저 기록된 후 메인보드 진입.
3. 고유 적 처치 이벤트 13건 → 한 번의 의뢰 레벨업/3장 플러그인 선택.
4. 플러그인 보상 화면 표시 이전 E의 3장 카드·RNG 체크포인트, 재추첨 시 정확히 1장만 변경·E 영구 기록. 선택 전에는 C 보유 레벨 미변경; E 승인 후 C·B 효과 레벨이 일치.
5. D CPU 목표 및 보스 사실 → E의 유일한 영수증/정화 기록.
6. D 철수 준비 → A의 일반·레어 학습 선택 UI → E 성공 시 CPU 철수/허브 복귀.
7. 학습 가능 플러그인 선택 시 보유 레벨 보존, 허브 수동 보관 트랜잭션.
8. 출전 경험치/보상/영수증 상태 불일치 시 오류로 판정, 원본 저장 미사용.
9. `hardware_cleansed` E ACK 후에만 3장 스킬 초안이 열리고, 선택한 스킬이 E `known_skills`와 B 활성 슬롯에 반영되는지.

신규 `tests/rework/integration/skill_draft_boss_pressure_smoke.gd`는 같은 시드/구역/보유 스킬의 결정적 초안, 습득 스킬 제외, 벽을 통과하지 않는 점멸, 보스 유예·텔레그래프·패턴 발사를 확인한다. 신규 C의 `plugin_live_effects_smoke.gd`, D의 `cpu_vertical_slice_smoke.gd`, 기존 B/C/D/E/A 10개 smoke도 동시에 Linux/Windows CI에서 실행한다.

## 미완료: 릴리스 차단

- **B #119 정식 CPU 전투 어댑터는 A의 새 façade를 통해 D 라우터에 연결되었음.** 다만 C #117에서 **27종 중 23종만 실제 B 전투 상태 변화로 검증**했고, 보호막 3종과 레어 지급 1종은 미완료. A 저장형 CPU 장면의 수동 Windows 플레이와 모든 빌드 시너지는 미검증. 스킬 발견 UI와 B 로드아웃 동기화는 자동 검증했지만, 실제 마우스/키보드 플레이 감각과 승인된 스킬 풀은 아직 아님.
- UI/UX 리워크 전체: 정식(승인된) 스킬 풀·밸런스, 스킬 상세/툴팁·키 리매핑, 백신 능력치 투자·무료 재분배 UI, 상세 보관·출전 관리, 카드 레벨 설명/신화 등급 연출, 접근성. 사운드·글로우/안개·보스 텔레그래프는 **초안 수준**으로만 연결됨.
- 하드웨어 GPU/RAM/SSD/HDD **완전한 플레이 장면과 보스/기믹**, 5개 자유 정화/전체 정화 보너스 실전 루프.
- E #118에 3장 카드·RNG·재추첨·천장 카운트 체크포인트를 추가했고, **CPU의 맵 시드·생성기 버전 사전 영구 저장을 연결했음**. 나머지 GPU/RAM/SSD/HDD 입장 전 체크포인트, 전투 상태 재현·중단 정책, 조합 불가능한 발사체 형상과 신화 플러그인 기획은 미완료. **완전한 재시작/의뢰 재개는 아직 허용되지 않음**.
- 백신 파기/출전/저장 장애 **실제 Windows 강제 종료·복구 QA**, UI 기반 재개/오프라인 복구 정책, 서버 없는 단일 플레이어 슬롯의 다중 프로세스 경합 처리.
- 8~12분/하드웨어, 40~60분/전체 정화, Windows GPU 프레임타임 p95/p99, 다양한 DPI/화면비/오디오 체감은 **실측 전**.

## #120 A 통합에서 검증된 범위와 잔여 인터페이스

- 통합 대상: B #119 (production combat), C #117 (23/27 실전 효과), D #116 (실시간 CPU), E #118 (추가 체크포인트·읽기 전용 복구 확인).
- A 연결: `scripts/rework/integration/production_b_world_facade.gd`. B/D의 인자 개수와 적 몸체 키 차이를 이 façade에서 대응하되 B의 피해·체력·중복 적중 판정을 복제하지 않음. C 효과는 B #119의 `c_effect_adapter.gd` 경로 하나로만 실행해 이중 적용 방지.
- A 저장: C의 고유 카드 3장·RNG 문자열을 먼저 E에 checkpoint; 재추첨도 E가 인정하면 UI 반영. 선택 후 E ACK를 검증하고 B/C 실시간 플러그인 레벨 반영.
- A 저장 오류: B/D 물리 틱까지 일시 정지. 잠금·손상·진행 중이던 구 의뢰를 무단 초기화하지 않음.
- **CPU 지역 시드 저장 경계 해결:** D의 게이트는 CPU 맵 생성 전 A의 E `checkpoint_region` 성공 ACK를 필수로 요구. 매번 동일한 `run_id:CPU:map-checkpoint` 영수증, D 알고리즘 버전·시드 불변성 보호. CPU 별도 재진입, 하드웨어 4종의 실제 장면 및 전체 5구역 루프는 별도 개발 필요.
- **남은 저장 복구:** E `inspect_slot`/영수증 복구는 읽기 전용만 제공함. 시드 체크포인트는 맵 복원에 필요한 일부 데이터일 뿐, 적 위치·체력·플러그인 전투 상태·의뢰 시간·UI 상태의 완전한 복원을 의미하지 않음. 사용자 승인 없는 강제 종료 후 임무 재개/자동 포기 금지.
- `tests/rework/world/cpu_vertical_slice_smoke.gd`가 E의 저장된 CPU 맵 시드와 D의 맵 생성 버전이 일치하는지 및 B의 실제 투사체/적 HP를 통해 보스·정화까지 확인한다. `tests/rework/integration/rework_pilot_smoke.gd`는 합성 적 사망 XP와 실제 E 저장·보상·추출 경계를 별도로 검증한다.
- 각 소유 PR과 #115의 Draft는 보존. #120는 **합성 검증 브랜치**이므로 main에 직접 병합하지 않고 안전한 PR 분리·리뷰가 선행되어야 한다.

## PR #121: 무작위 레어 플러그인의 E 원자적 지급

- 검증용 변경은 PR #121이며, 합성 통합 기반 PR #120에 쌓여 있다. 둘 다 Draft, main 병합 금지.
- E rare_bonus.gd는 기존 v1 저장 포맷의 environment_rolls 아래 e_rare_bonus_v1 기록만 추가한다.
- E는 source plugin_picked와 레어 보너스를 하나의 파일 트랜잭션으로 저장하고 서로 다른 두 영수증을 발행한다.
- 현재 후보는 C의 정식 rare 목록 중 최대 레벨 미달 플러그인이다. 후보 소진 시 부분 지급 없이 거절한다.
- 난수 후보는 의뢰 시드, 런 ID, 소스 카드 영수증으로 결정되고 결과를 저장한다. 중복 요청은 보너스를 다시 지급하지 않는다.
- A는 영구 저장을 검증한 후에만 C 카드 레벨과 B 실제 전투 레벨을 변경한다.

## 후속 A 검증: 읽기 전용 저장 진단 (PR #122 후보)

- 별도 CPU 파일럿이 기존 실행 중 의뢰, 검증할 수 없는 저장 파일 또는 E 영수증 실패로 안전 정지하면 게임이 멈춘 상태에서도 **읽기 전용 저장 진단 패널**을 보여 준다.
- 확인 가능한 E 리비전, 의뢰 ID, 정화 수, 남은 재추첨·보상 체크포인트를 보여 주며, 영수증을 알고 있는 실패 이벤트는 E `reconcile_receipt`를 읽기 전용으로 호출해 저장됨/확인된 미기록/확인 불가를 구별한다.
- `nv_c_random_rare`를 지급한 카드의 저장 ACK가 유실된 경우, **E 원본 영수증·파생 레어 영수증·저장된 레벨을 함께 확인**했을 때만 두 보상이 기록됐다고 보여 준다.
- 패널에는 재검사 버튼만 있다. **의뢰 자동 재개, 자동 포기, 같은 영수증 재전송, 보상 지급, DB 수정, 손상 파일 복구는 제공하지 않는다.** 읽기 성공 자체는 게임 재개 승인에 해당하지 않는다.
- 신규 A 전용 smoke `tests/rework/integration/pilot_recovery_view_smoke.gd`는 중단 의뢰 재실행 UI, E 원자적 레어 지급 뒤 ACK 유실, 미기록 영수증, 유실/검사 전후 리비전 불변, 불가독 슬롯을 Linux·Windows CI에서 검증하도록 연결했다.
- 자동 테스트 결과와 실제 Windows QA는 별개다. 정식 중단 의뢰 재개/포기 정책 및 E/C 소유자 계약 반영 이전에 이 브랜치를 `main`에 직접 병합하지 않는다.
